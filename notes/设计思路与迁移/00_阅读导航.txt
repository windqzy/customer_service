一、先看懂这份指南与旧笔记的区别

  旧笔记：通过比喻理解某段代码。
  当前代码文本架构图.txt：按文件和调用顺序定位代码。
  本目录：解释为什么这样设计、哪些可复用、迁移时如何改。

本指南统一使用三个标记：
  [当前] 已在当前源码中存在的实现，不代表经过完整上线验证。
  [未接通] 有模型、组件或分支，但还没接入完整调用链。
  [迁移建议] 面向下一个项目的设计选择，尚未写入本项目代码。

不要将“有一个类”“有一个配置项”直接当作“功能已经跑通”。
每次代码演进后，应重新核对真实的调用入口、返回值和状态修改位置。

三、整个系统的设计主线

  业务规则定义        用户运行状态         本轮输入
  FlowCatalog        DialogueState        UserMessage
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ▼
                       TurnPlanner
                           │ TurnPlan：本轮建议的命令
                           ▼
                     TurnPlanValidator
                           │ 合法计划才能进入执行（目标边界）
                           ▼
                      CommandProcessor
                           │ 更新任务状态、产生 TaskEvent
                           ▼
                       FlowExecutor
                           │ 根据步骤继续/追问/调用动作/结束
                           ├─ ActionRunner → 业务接口 [已接入，见 04]
                           └─ ResponseRender → 模板回复
                           ▼
                生命周期提示 + 步骤回复 → BotMessage 列表
                           ▼
                  保存 DialogueState → 返回 API 响应

四、迁移时先保留什么，再替换什么

优先保留：
  分层职责、数据协议、状态机思路、规划与执行分离、注册表、
  统一结果模型、显式依赖、资源生命周期、可替换外部系统的测试方式。

按业务替换：
  YAML 流程、槽位名称与类型、意图目录、提示词示例、
  具体 Action、外部接口地址与鉴权、回复文案、API 入口协议。

按规模决定是否增加：
  配置版本、并发控制、请求去重、动作幂等、历史归档、执行观测。

不要先照搬整个目录树。先确认新项目是否真的需要多轮状态、
固定业务流程和多种业务动作；只有单次问答时可以保留更少的层。

五、设计概念速记

  规则 = 可以怎么做。
  状态 = 这位用户当前做到哪里。
  计划 = 本轮建议做什么。
  命令 = 请求改变什么。
  事件 = 刚刚发生了什么。
  动作 = 实际调用哪个业务能力。
  回复 = 用户最后看见什么。

本次只整理文档；没有修改业务代码，也没有调用数据库、商城或大模型。
