规划、校验与配置化流程
基线：075805a；代码路径均相对于项目根目录。

一、为什么让模型负责规划，程序负责执行

问题：
  用户的自然语言有省略和歧义，但业务步骤、参数来源和执行条件需要明确。

方案：
  自然语言理解 → 结构化计划 → 程序校验 → 状态更新 → 按流程执行。

  用户：“订单是 1001，帮我查物流”
       ↓ Planner
  start_flow(logistics_tracking) + set_slots(order_number=1001)
       ↓ Validator
  检查流程、命令和状态是否合法
       ↓ Processor / Executor
  建任务、填槽位、执行相应步骤

收益：
  可以独立观察模型是否理解正确，以及执行器是否执行正确。
  模型不用记住每个接口地址和具体步骤；程序不必硬编码所有自然语言表达。
  计划可记录、可模拟、可回归检查。

代价：
  要维护提示词、模型输出结构和执行协议的一致性。
  多加了一层解析和校验，并不是模型返回 JSON 就天然可靠。

代码锚点：
  atguigu/plan/turn_planner.py
  atguigu/prompts/jinja2/turn_plan.jinja2
  atguigu/plan/models.py
  atguigu/plan/command.py
  atguigu/plan/turn_plan_validator.py

二、提示词输入是一份明确的数据协议

当前输入：
  user_message            当前消息，经 HistoryBuilder 转为文本。
  conversation_history    当前 Session 中之前的聊天轮次。
  task_state_json         当前任务和暂停任务，包括已填槽位。
  focused_object_json     当前指向的订单/商品或 null。
  flows_json              Flow 概况与输入槽位定义，不包含完整 steps。
  knowledge_intents_json  当前为 {}，知识意图目录尚未接入。

为什么当前消息和历史分开：
  当前消息是本轮行动依据；历史帮助理解“这个”“还是刚才那个”。
  如果把历史请求再次当作当前请求，可能重复启动业务。

历史不等于全部状态：
  active.step_id 和 slots 是程序可执行的进度，不应每次靠模型从聊天记录猜出来。
  历史用于理解，结构化状态用于明确执行位置。

迁移检查：
  提示词变量名与调用字典逐个对应。
  截取最终渲染后的提示词，确认真实用户消息已传入。
  为长历史设置截取或摘要策略，保留当前问题、当前任务和必要事实。
  若更换模型供应商，保留计划协议，单独检查 JSON 格式和语义表现。

本项目经验：
  曾把 user_message 传成 {}，模型收到空输入；依赖注入本身没有问题。
  所以诊断顺序应包含“模型实际看到了什么”，不能只看输入变量定义。

三、结构化计划既是边界，也是可替换点

TurnPlan 的三条方向：
  task       → commands
  knowledge  → intents
  chitchat   → 闲聊标记

Command 协议：
  start_flow  → 开启某个 Flow
  set_slots   → 给当前业务补充参数
  resume_task → 恢复指定 task_id
  cancel_task → 取消指定 task_id

模型 JSON 经 TurnPlan.from_dict() 转为 Python 对象。
Command.from_dict() 根据 command 字符串选择具体命令类。
这让执行器只依赖稳定的数据协议，不依赖模型原始文本格式。

迁移时要定义输出协议版本或至少统一维护一份结构说明。
未知命令、缺字段、字段类型错误，应转为可诊断错误，不要只靠 KeyError 退出。
当前使用 JsonOutputParser + 手写 from_dict，并未实现完整的输出错误处理。

四、校验要在执行前真正起作用

建议区分三层：
  语法层：是不是合法 JSON、字段是不是完整、类型是不是匹配。
  目录层：flow、intent、slot、action 名称是否存在。
  状态层：当前任务是否允许这条操作，目标任务是否属于当前状态。

有效的控制流应是：
  解析失败 → 不执行任务，返回可理解的错误或澄清。
  校验失败 → 不执行任务，返回澄清。
  校验通过 → 执行命令和步骤。

[当前]
  已实现方向数量、部分流程和任务存在性检查。
  Engine 的校验失败分支仅 pass，所以尚未形成执行阻断。
  提示词允许明确多请求同时命中方向，而 validator 会拒绝多个方向。

[迁移建议]
  先确定业务策略：单方向就明确澄清选择；多方向就定义执行顺序和失败处理。
  提示词、validator 和分发代码遵循同一策略。
  一批命令按顺序执行时，应考虑前一条对后一条的影响：
    start_flow + set_slots 必须在同一批计划中能够正确校验。
  可先在临时状态上演练整批命令，全部合法后再修改正式状态。

五、为什么把业务流程写在 YAML 中

问题：业务步骤、追问话术和条件跳转频繁改变，但步骤类型相对稳定。

方案：
  YAML 定义业务内容，Loader 负责解析，Executor 解释步骤。
  新增同类业务流程时，优先增加配置和 Action，而不是复制整个执行循环。

解析路径：
  YAML → dict → FlowSlot / FlowStep / Flow → FlowCatalog

目前支持的步骤：
  start     开始并推进。
  collect   有值则推进，缺值则追问并返回。
  action    调业务系统；已接入 Runner 调用、注册表组装和结果写回。
  response  渲染模板、收集回复、推进。
  end       清空当前活动任务并返回回复。

next 可以是固定链接、条件链接和兜底链接。
实际执行根据 step_id 和 next，而不是简单遍历 steps 列表顺序。

适用场景：
  表单收集、多轮客服、审批引导、报修、预约等步骤可定义的任务。
不必强行使用的场景：
  单次查询接口或没有稳定步骤的开放式对话。

六、流程暂停实际上是保存状态后结束本次调用

  第一次请求：start → collect，缺少字段
        ↓
  回复追问，step_id 停在 collect，保存状态，HTTP 请求结束
        ↓
  下一次请求：加载状态，Planner 输出 set_slots
        ↓
  更新槽位，再执行 collect，已有值，继续推进

收益：
  无须为每个用户长期保留一个正在等待输入的 Python 函数。
  进程重启后，只要状态和对应流程定义仍可读取，就能恢复执行位置。

代价：
  必须明确持久化时点、流程版本、重复请求以及并发写入的策略。
  Action 产生外部副作用时，不能仅用一个 step_id 保证“只执行一次”。

七、迁移前给配置加哪些检查

建议在加载阶段检查：
  flow ID、step ID 是否重复。
  每个流程是否有合法 start；每个 next 是否指向存在的步骤。
  collect.slot_name 是否在槽位目录中。
  action 名称是否已注册。
  response 模板引用的字段是否有可说明的数据来源。
  哪些分支可以到达 end，循环是否有合理停止条件。

这是迁移建议；当前 Loader 主要做字典到对象的转换。
当前条件跳转使用 eval；迁移时优先采用受限条件操作符或可信表达式解释器，
并保持配置的管理边界，不把用户文本直接当作可执行表达式。

循环上限只是最后的保护：到达上限应产生明确错误，而不是悄悄返回 None。
同样，只有一个条件链接也应检查条件，不能只看链接数量就直接跳转。
